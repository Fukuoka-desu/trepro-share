終章

強いハーネスを、強いまま運用し続ける 最強のまま保つ

『本書を最後まで読んだ』。 これは到達点ではなく、運用の出発点です。

ほとんどの人は、教科書を読み終わると、そのまま閉じてしまいます。 ですが、AI の領域では、最強の状態を維持することそのものに継続的な手入れが必要です。

この終章で扱うのは、強いハーネスを強いまま運用し続けるための原則です。 人が変わる、組織が変わる、AI が変わる──それでも崩れない設計の見直し方を持っておきます。

読み終わったその日から、本書は『更新し続ける起点』として動き始めます。

実装リファレンス

  1. 原則と変動情報を分ける。
  2. 全TopicをSource IDで追跡する。
  3. SNS/動画は発見、仕様は一次資料で確定する。
  4. 読了率より成果物とCheckを測る。
  5. Harnessと教材を同時更新する。

【なぜこの設計か】 原則、変動情報、Source、Checkを分けて点検すると、仕様変更のたびに教科書全体を書き直さずに済みます。週次では古い確認日と失敗したCheckを拾い、月次ではCoverageとSkill運用の偏りを見直します。読了率だけを追うと、教材が読まれていても古い操作や失敗するSkillを残します。

最終形は「Claude Codeの使い方を説明する本」ではない。

全社員が安全で再現可能な型を使い、成功した仕事をSkillへ昇格させ、そのSkillを評価・配布・改善し続けるための組織OSである。

【なぜこの設計か】 Harnessと教材を同時に更新すると、配布された制御と学習した手順が食い違いません。Skillだけ更新すると教材が古い入力を教え、教材だけ更新すると端末に必要な制御が届きません。同じRelease記録から両方の差分を確認することで、「最強」を一時点の機能数ではなく更新可能な状態として保てます。

【実演】 今週の点検を行い、その四週分を月次Reviewへ束ねる場面です。自動修正や配布は行いません。

依頼文

Project内のFeature Registry、Source ID一覧、Coverage Map、Skill検証結果、Harness Release記録を読み、週次点検を実行してください。
確認日が古い変動情報、Sourceへ戻れないTopic、失敗したCheck、教材とHarnessの差分を抽出してください。
確認できない項目は未確認とし、推測でPASSにしないでください。
今週の結果をreviews/week-current.mdへ、四週分が揃っている場合は傾向と未解決項目をreviews/month-current.mdへまとめてください。
各Findingに根拠File、状態、次の確認Actionを付けてください。
Registry更新、Skill配布、Policy変更、公開は実行しないでください。
完了条件は、週次の各Findingを根拠へ戻せ、月次では継続、解消、新規を区別できることです。

Claude Codeが何をするか

最初に五種の運用Artifactが存在し、読めるかを確認します。次に古さ、Coverage、Check、教材とHarnessの差分を根拠付きで分類します。四週分があれば月次の変化へまとめ、修正や配布はせず次のActionを提示します。

成果物

reviews/week-current.mdに今週の点検結果ができ、条件を満たす場合はreviews/month-current.mdに四週の傾向ができます。未確認や未解決も消さず、根拠と次の確認Actionが残ります。

検証方法

各FindingのFileを開き、記載された状態を再確認します。週次の件数と月次の継続、解消、新規の合計が対応するかを見ます。DiffでRegistry、Skill、Policy、公開物が変更されていないことを確認して点検完了とします。

出力は例示であり、Version・環境で異なります。

更新時に必ず持つ：

これは何か 更新時に必ず持つメタ項目リスト。verified_at・minimum_version・status・plans・official_source・migration_noteの6項目を最小単位で並べています。

実行するとどうなるか Registry更新時の必須欄として強制でき、確認日や移行手順のない古いエントリが残り続ける事故を構造的に防げます。

それぞれの意味

verified_at
そのエントリを最後に確認した日付です。書かないと有効期限が分からず、古いまま信頼され続けてしまいます。
minimum_version
動作保証する最小バージョンです。書かないと古い環境の読者が動かない手順を踏むことになります。
status
Active/Suspended/Deprecated等の現在状態です。書かないと停止済み機能を案内し続ける事故が残ります。
plans
利用可能なPlan区分です。書かないと自分のPlanでは使えない機能を読者に勧めてしまいます。
official_source
一次資料の参照先です。書かないと出典が辿れず、改訂時に誰のソースか分からなくなります。
migration_note
Deprecated項目に添える移行手順です。書かないと利用者が古い手順から安全に抜けられず取り残されます。

おわりに ── 読者へ

ここまでお読みいただき、ありがとうございました。

40章を一気に通読された方も、14レッスンを順に進めながらここに辿り着いた方も、 読み終えた瞬間に共通して持つ感覚があるはずです。 『これは、続きを書く本だ』ということ。

Claude Code は、本書を執筆している間にも進化しました。 Skills のメニュー配置が変わり、Permission Mode の名称が変わり、MCP の対応サービスが増えました。 だから本書は『完成版』ではなく、『あなたの仕事に合わせて更新する起点』として書かれています。

最後に、3つだけお願いがあります。

ひとつ、第4章の90分実習は必ず手を動かしてください。 読むだけでは、本書の85%は身につきません。

ふたつ、CLAUDE.md と Skills は、自分の言葉で書き直してください。 本書のテンプレをコピペするのではなく、あなたの仕事のリズムに合わせて書いた一文だけが、 半年後も生き残ります。

みっつ、もし本書を会社で配るのであれば、配って終わりにしないでください。 3か月後に、配った相手と一緒に振り返る場を持つこと。それだけで、組織の AI 活用は明らかに変わります。

本書は読み終わるための本ではなく、読み始めるための本です。 あなたの仕事に合わせて、ここから書き換えていってください。
